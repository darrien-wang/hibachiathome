# 线索扫描 v2（2026-10-21 随 leads v2 整理）

## 0. 为什么是这个样子

09-27 复盘：90 条线索 18 单成交，**没有一单是追出来的**；锁单几乎都发生在客人自己迈了一步之后（问下一步、给日期、打电话、重算报价、打开锁单页）。10/11–10/17 一周的数又印证了一次：f_one 跟进 71 条，14 天锁单 3%；客人迈步后递的锁单链接 9 条，锁单 56%。

所以扫描的目标按优先级是：

1. **不漏掉任何一个迈了步的客人**（回复、来电、重算报价、打开锁单页、派对页有动静）
2. **解掉挡在客人前面的东西**（没答的问题、错的价格、缺的链接或时间、"要等人数定了"这种误解）
3. **找出没说出口的异议**（订前问桌椅、卡在 $599、人数往下砍、说预算——都是预算在说话）
4. **该停的停**（3 条封顶、客人自设节奏、丢了的问一句原因再标）

追只是第 4 件事的一小部分。每条外发照样过 leads §0 的四问。

## 1. 命令

```
python scripts/desk/desk.py scan              # 全池分桶，一张表（并把桶写进 leads.segment / next_action_at）
python scripts/desk/desk.py scan --bucket D   # 只看一个桶，每条带完整卡（对话、报价、刹车预演）
python scripts/desk/desk.py scan --no-write   # 只看不写
```

分类逻辑在 `lib/lead-scan.ts`（接口 `GET /api/admin/scan`），**判据不靠记忆**。它读库里的时间线 + Twilio 的"每个号码最后一句"（谁最后说话以 Twilio 为准），不发任何东西。

## 2. 桶 → 动作（按这个顺序处理）

| 桶 | 判据 | 动作 |
|---|---|---|
| **A 欠回复** | 客人最后说话（短信或来电）；从没联系过的新线索也在这 | 立刻回（leads §3） |
| **C 热信号** | 48 小时内重算报价、打开锁单页、付款失败、派对页有动静，且我们之后没写过 | 10 分钟内动：答疑、递链接。**这是唯一该主动递链接的时候**（leads §5.5）。00:00–07:00 发生的，07:00 后第一件事 |
| **G 已付未齐** | 已锁单、派对 14 天内、缺地址/菜单/时间 | 按各自节奏催齐（leads §6），不受跟进刹车；客人说了哪天给的不催 |
| **B 承诺到期** | `[callback]` 到期、挂起已过，客人没再说话（最后只回了句客气话、已过 2 小时的也算） | 接着他自己的话问（leads `templates.md` §跟进 B 桶）；他等的是人数或名单 → 模板 L |
| **F 隐性异议** | D/E 里带 tables_asked / budget_words / at_minimum / headcount_down | 跟进就是那一次让步：订前问桌椅按 D-1017-01；卡最低消费的周中单可到 $500；说预算的先问数再让（leads §5.6） |
| **E 派对临近** | 日期 7 天内，没锁单 | 有新信息才发 f_deadline，一条为限；满 3 条的要 force，**先给老板看**；派对日过了没锁的标 lost |
| **D 到期跟进** | 我们最后说话（客人最后只回了句客气话、已过 2 小时的也算：那句不补，照常跟进）、≥20 小时、未满 3 条、无挂起无 callback | f_one：台阶句 + 一个真理由 + 一个好答的问题（leads §5.3），发完满 3 条的挂 14 天 |
| **H 停** | 挂起中 / 满 3 条 / 打不通 / 刚发过不到 20 小时 / 最后一条是点赞 | 不发。`needs_hold` 的挂 14 天；点赞的 `ack` |

旗标（挂在任何桶上，是数据修的清单）：`name_unknown`、`city_default`、`travel_underquoted:$N`（报价说免路费但路费表有费用）、`has_paid_order`（状态该是 won）、`tapback_last`、`cap_reached`。

**顺序就是 A → C → G → B → F → E → D → H。** A 和 C 不等。

## 3. 谁批（按 leads §4）

- **直接发、发完报**：A/C/G 的回答和催齐；B 接他的话；D 的 f_one（含改了措辞的，D-1013-05）；F 里带宽内的那一次让步；E 里没满 3 条的 f_deadline。
- **先给老板看**：低于底线的让价、破 $599/$500、满 3 条还要 force、严重投诉、61+ 低于每人 $45。
- **节奏**：主动短信 10 分钟内 ≤6 条（系统 `sweep` 刹车），超了拆两批、隔 10 分钟。一条一条读、一条一条写，不套同一句批量发。

## 4. 发之前必做（09-29 两次都栽在这）

1. **重读对话**：`desk card <id>` 或 `desk thread <phone>`，看最后一条是谁说的。Nasim 那次用 19 秒前的对话拟稿，把她刚拒绝的方案又推了一遍。
2. **查撞车**：客人上一句之后，别的发送方 15 分钟内回过（409 `just_answered`）：同一件事跳过、不补发；另一件事等窗口过了再发。
3. **有日期的不许再问日期**（系统 409 `asked_known_date`）；没日期的才问周末。
4. **价格先过引擎**（`desk price`），短信里不出现没算过的数。
5. **看挂起理由**：挂起到期的线索在扫描里是休眠、不进 D；`desk card` 上 ⏸ 后面写着为什么挂，发之前读一眼。

## 5. 频率

| 时段 | 做什么 |
|---|---|
| 老板问"有新回复/新线索吗" | A、C（`desk next` 也行，它只看在等的） |
| 每天 10:00、16:00 PT | 全池扫描，所有桶；旗标顺手修 |
| 每天 16:00 | 明天派对逐单 `desk order remind <单号> --dry` 看一眼尾款再发 |

扫描由处理线索的会话手动跑。机器那边由 Supabase pg_cron 管（首响 A/B、派对前 72/48/24 小时确认、收件箱提醒），见 leads `tools.md`。

## 6. 写回

- 每条发出去的用桶做前缀记备注：`[SOP:f_one]`、`[SOP:f_deadline]`、`[SOP:deposit_ask]`、`[SOP:tables]`、`[SOP:b_callback]`、`[SOP:g_menu]`……周报按前缀算每类的回复率和锁单率
- 客人说的原因记 `[why]`，场合记 `[occasion]`，自报时间记 `[callback]`
- 发完满 3 条的立刻 `desk hold <id> 14`；H 里 `needs_hold` 的也挂
- `has_paid_order` 的把状态改 won；`travel_underquoted`（报价按城市、实际地址更远）**按实际路费收**（老板 10-22），改订单后马上一句话告诉客人新总价


## 8. 怎么知道它有没有用（按周，进周报）

- **首响中位**：目标 ≤10 分钟（09-27 基线 29 分钟、p90 103 分钟）
- **每类外发的 48 小时回复率、14 天锁单率**：10/11–10/17 基线 first_response 43%/7%、f_one 23%/3%、deposit_ask 89%/56%、tables 78%/11%、f_deadline 38%/0%
- **池转化率**：报价后沉默 >24h 的线索，14 天内锁单的比例
- **信号命中**：C 桶从信号到我们动的中位分钟数
- **STOP 率、未送达率**：STOP 超过 2% 或出现一次垃圾短信投诉，告诉老板、把跟进再收紧

数据从 `[SOP:*]` 备注 + `lead_touchpoints` 里算，`desk report week` 出数；做法见 `docs/销售日志/README.md`。

## 9. 不做的事

- 不群发（09-23 的 24 条、09-27 审计的 9 次群发都是反例）
- 不给沉默的人连发链接（零转化）；不编"快满了"；跟进里不说 "still open"；不写"最后一条"的口气
- 客人自设的回话时间之前一条不发
- 不替客人确认派对页的默认菜单（09-29："默认就默认"）
- 不对客主动更正我们报错的价格，备注里记下来等老板定
