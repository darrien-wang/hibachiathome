# 线索扫描（2026-10-01 起试行一周，攒数据再定要不要自动化）

## 0. 为什么是这个样子

09-27 复盘：90 条线索 18 单成交，**没有一单是追出来的**；押金几乎都发生在客人自己迈了一步之后（问下一步、给日期、打电话、重算报价、打开押金页）。09-29 第一次全池扫描发了 10 条跟进，有价值的回复来自两处：Corrina 付押金是因为一句"不用等人数定了才订"解掉了她的顾虑；Melissa 是因为我们问了她为什么选别家。

所以扫描的目标按优先级是：

1. **不漏掉任何一个迈了步的客人**（回复、来电、重算报价、打开押金页、planner 里动过）
2. **解掉挡在客人前面的东西**（没答的问题、错的价格、缺的链接/时间、"要等人数定了"这种误解）
3. **找出没说出口的异议**（订前问桌椅、卡 $599、人数往下砍、说预算——都是预算在说话）
4. **该停的停**（3 条封顶、客人自设节奏、丢了的标清原因）

追只是第 4 件事的一小部分。

## 1. 命令

```
python scripts/desk/desk.py scan              # 全池分桶，一张表（并把桶写进 leads.segment / next_action_at）
python scripts/desk/desk.py scan --bucket D   # 只看一个桶，每条带完整卡（对话、报价、刹车预演）
python scripts/desk/desk.py scan --no-write   # 只看不写
```

分类逻辑在 `lib/lead-scan.ts`（接口 `GET /api/admin/scan`），**判据不靠记忆**。它读库里的时间线 + Twilio 的"每个号码最后一句"（谁最后说话以 Twilio 为准），不发任何东西。

## 2. 桶 → 动作（按这个顺序处理）

| 桶 | 判据 | 动作 | 谁批 |
|---|---|---|---|
| **A 欠回复** | 客人最后说话（短信或来电）；从没联系过的新线索也在这 | 立刻回：事实直发；聊类拟稿；新线索发 §3.1 模板 | 事实/模板/客气收尾直发 |
| **C 热信号** | 48 小时内重算报价、打开押金页、付款失败、planner 有动静，且我们之后没写过 | 10 分钟内动：答疑、递链接。**这是唯一该主动递链接的时候** | 事实直发 |
| **G 已付未齐** | 已付押金、派对 14 天内、缺地址/菜单/时间 | 运营催齐，不受刹车；周六清单在这里 | 直发 |
| **B 承诺到期** | `[callback]` 到期、挂起已过，客人没再说话 | 接着他自己的话问："You said Friday - how did it land?" | 拟稿 |
| **F 隐性异议** | D/E 里带 tables_asked / budget_words / at_minimum / headcount_down | 跟进就是那一次让步：桌椅换锁日期（leads §8）、周中 $500 底线（§4.3）、先问数再让 | 带宽内直发，超带宽问老板 |
| **E 派对临近** | 日期 7 天内，没付押金 | 真时钟 + 开门句（§4.2 f_deadline）；已满 3 条的要 force，**先给老板看** | 拟稿 |
| **D 到期跟进** | 我们最后说话、≥20 小时、未满 3 条、无挂起无 callback | 台阶句 + 一个真理由 + 一个好答的问题（§4.2 f_one）。**这是这条线索的最后一条** | **一批一次批** |
| **H 停** | 挂起中 / 满 3 条 / 打不通 / 刚发过不到 20 小时 / 最后一条是点赞 | 不发。`needs_hold` 的挂 14 天；点赞的 `ack` | — |

旗标（挂在任何桶上，是数据修的清单）：`name_unknown`、`city_default`、`travel_underquoted:$N`（报价说免路费但路费表有费用）、`has_paid_order`（状态该是 won）、`tapback_last`、`cap_reached`。

**顺序就是 A → C → G → B → F → E → D → H。** A 和 C 不等；D 攒成一批。

## 3. 一次扫描一次批（用户 2026-10-01 定）

- A/C/G 里的事实、§3.1 首条模板、§1.04 客气收尾：**直发**，报告里带一行
- B/D/E/F：扫完**一张表**给老板（每条：客人 · 日期 · 桶 · 稿子），老板说一次"发"，按刹车节奏分批发（10 分钟内 ≤6 条主动短信，超了拆两批、隔 10 分钟）
- 超带宽（破 $500、31 人以上、投诉、满 3 条要 force）：单独标出来等老板

## 4. 发之前必做（09-29 两次都栽在这）

1. **重读对话**：`desk card <id>` 或 `desk thread <phone>`，看最后一条是谁说的。Nasim 那次用 19 秒前的对话拟稿，把她刚拒绝的方案又推了一遍。
2. **查撞车**：另一个会话可能在同时回客人（Alice、Andrea 各收到两条）。最后一条如果是我方 3 分钟内发的人工短信——跳过。
3. **有日期的不许再问日期**（系统 409 `asked_known_date`）；没日期的才问周末。
4. **价格先过引擎**（`desk price`），短信里不出现没算过的数。

## 5. 频率（试行周：手动）

| 时段 | 扫哪些桶 |
|---|---|
| 老板问"有新回复/新线索吗" | A、C（`desk next` 也行，它只看在等的） |
| 每天 10:00、16:00 | 全池：B、F、E、D 成批给老板批 |
| 每天 9:00 | H 家务 + G 周六派对清单 + 旗标数据修 |

**攒一周数据再决定自动化**（用户 2026-10-01 定）。定时任务要 app 开着且会卡权限审批；服务端 pg_cron 方案没批。

## 6. 写回

- 每条发出去的跟进用桶做前缀记备注：`[SOP:f_one]`、`[SOP:f_deadline]`、`[SOP:deposit_ask]`、`[SOP:tables]`……周报按前缀算每个桶的回复率
- 客人说的原因记 `[why]`，场合记 `[occasion]`，自报时间记 `[callback]`
- D 发完立刻 `desk hold <id> 14`（那是最后一条）；H 里 `needs_hold` 的也挂
- `has_paid_order` 的把状态改 won；`travel_underquoted` 的**不对客更正**，备注里记"到时候认不认老板定"

## 7. 报告格式（固定）

```
扫描 10-01 10:00 · 池 59
A 欠回复 2 → 已回 2
C 热信号 1 → 已处理（重算报价，答了差价）
G 已付未齐 3 → 已催（Frank 地址、Caleb 菜单、Alice 菜单）
D 到期跟进 10 → 稿子见下表，等你一个"发"
F 隐性异议 2 → 桌椅换锁日期 ×1（已发）、$500 底线 ×1（等她报数）
H 停 7 → 已挂起
旗标 3 → 已修 / 待定
待你定：……
```

## 8. 怎么知道它有没有用（按周）

- **首响中位**：目标 ≤10 分钟（复盘基线 29 分钟、p90 103 分钟）
- **池转化率**：报价后沉默 >24h 的线索，14 天内付押金的比例（09-19 基线 11 池 1 中）
- **每个桶的回复率**：09-29 D 桶台阶句 10 条回 3 条，对照旧第 3 条 15%；攒够 30 条再下结论
- **信号命中**：C 桶从信号到我们动的中位分钟数

数据从 `[SOP:*]` 备注 + `lead_touchpoints` 里算；周报做法见 `docs/销售对话对抗性复盘-2026-09-27.md`。

## 9. 不做的事

- 不群发（09-23 的 24 条、09-27 审计的 9 次群发都是反例）
- 不给沉默的人连发链接（零转化）；不编"快满了"；不说"still open"
- 客人自设的回话时间之前一条不发（§4.4）
- 不替客人确认 planner 默认菜单（用户 09-29："默认就默认"）
- 不对客主动更正我们报错的价格（用户定），备注里记下来等老板定
